## 2. 应用场景与问题背景

### 2.1 场景

移动通信基站的能耗具有强烈的**"话务—功耗不匹配"**特征：一个扇区的功耗中约 **60%~70% 是与话务量无关的静态开销**（功放偏置、基带常开、射频链路维持）。这意味着：

> 即便凌晨 3 点扇区里只有 3 个用户、PRB 利用率不到 5%，该扇区仍然在消耗接近 70% 的峰值功耗。

在网络规模化的前提下，这部分"空载能耗"是运营商 OPEX 与碳排放的重要组成部分。业界通行的应对手段是**小区/扇区休眠**（Cell Sleep / Cell DTX），但工程落地长期受限于一个两难：

- **不做休眠**：夜间空载能耗被白白浪费；
- **粗暴休眠**（定时开关、随机休眠）：一旦话务突增或用户分布变化，就会造成接入失败、切换掉线，用户体验直接受损。

### 2.2 现有方案的痛点

| 现有做法 | 痛点 |
|---|---|
| 固定时段定时关断 | 无法感知话务实际变化，节假日/突发事件下必然误判 |
| 基于简单阈值的规则 | 只判"能不能睡"，不判"睡了代价多大"，缺乏权衡 |
| 人工经验配置 | 不可扩展、不可审计，人员变动即失效 |
| 强化学习类方案 | 决策不可解释、训练不稳定、冷启动风险高，难以通过运维审核 |

### 2.3 本项目的切入点

把"该不该睡、睡哪几个、睡多久"变成一个**显式的、可审计的多目标优化问题**：在满足用户服务约束（未服务用户占比 ≤ 1%）的前提下，最大化节能量。决策由确定性代码完成，大模型只负责事后解释——这样既拿到了自动化的收益，又保住了运维最看重的**可解释与可追责**。

## 3. 核心价值

### 3.1 直接价值：降低夜间空载能耗

在用户无感知（未服务比例 ≤ 1%）的前提下，对夜间低负载扇区实施自主休眠，直接削减基站静态功耗。MVP 仿真中已验证该机制可稳定产生可观的节能幅度（见 §6）。

### 3.2 差异化价值：可审计的 AI 决策

| 传统 AI 方案 | 本项目 |
|---|---|
| 神经网络输出一个动作，无法解释 | 输出"为什么选这个组合"的完整算式 |
| 同一输入可能得到不同输出 | **同一输入必得同一输出**（无随机、LLM 不用数值） |
| 出问题只能整体回滚 | 每 15 min 决策可逐条复算、定位 |
| 需要大量数据训练 | 无训练过程，规则与权重显式可调 |

这段话是本项目与"又一个 AI 节能 demo"的根本区别：**我们不追求"AI 感"，我们追求"运维敢用"**。

### 3.3 对 Pre6G 试验网的价值

1. **AI 内生融合的场景验证**：Pre6G 强调"AI 内生"，本项目提供了一个"AI 参与网络运维但决策可控"的具体样本——LLM 负责交互与解释，确定性算法负责控制，这正是 6G 网络智能体的合理分工形态；
2. **绿色网络指标积累**：产出 7 天连续的小区级能耗-QoS 对照数据，为后续节能标准与能效评估方法提供参考；
3. **可复用的验证范式**：本项目的方法（离线回放 + 双组对照 + 逐条审计）可直接迁移到其他网络智能体场景（负载均衡、移动性优化等）。

## 4. 技术路线概述

```
只读 KPI / 合成数据
        │
        ▼
┌───────────────────┐
│ 扇区状态采集工具   │  每 15 min 拉取一次快照
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 候选筛选           │  低负载 + 具备休眠能力
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 组合枚举 + 加权打分 │  score = w_e·ΔE − w_q·U_unserved
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ QoS 独立复核       │  越界 → 放弃休眠，保持全开
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 审计 + 突发回滚    │  负载跳变 > 25pp 立即撤销休眠
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ LLM 生成解释（仅此）│  Ollama 本地小模型，不参与数值
└───────────────────┘
```

技术细节见《技术方案》（`docs/technical-proposal.md`）。

## 5. 系统边界与安全声明（重点）

> 本节为本项目申报的核心合规说明，请审核方重点关注。

### 5.1 一句话边界

> **本项目不控制任何真实基站硬件。** 仅申请**只读流量负载接口**与**模拟决策回传接口**；所有"休眠指令"只做本地记录与日志归档，**绝不下发至真实设备**；项目**不具备任何网络硬件操作权限**。

### 5.2 权限矩阵

| 能力 | 是否申请 | 说明 |
|---|---|---|
| 读取小区/扇区负载（PRB 利用率） | ✅ 申请 | 只读、15 min 粒度、扇区级聚合 |
| 读取扇区在线用户数 | ✅ 申请 | 只读、扇区级聚合，不含用户标识 |
| 上传模拟决策日志 | ✅ 申请 | 单向写入日志服务器，不触达网元 |
| 修改基站参数 | ❌ 不申请 | — |
| 执行扇区关断 / 小区闭塞 | ❌ 不申请 | 休眠仅记录，不执行 |
| 登录网元管理面（SSH/SNMP Set/NETCONF 写） | ❌ 不申请 | 无任何写通道 |
| 访问用户级数据 / 信令内容 | ❌ 不申请 | 仅聚合统计量 |

### 5.3 代码层面的硬约束

本项目的开源仓库中：

1. **没有任何 HTTP 写方法**（`POST/PUT/PATCH/DELETE` 调用），只有本地文件读写与只读数据源解析；
2. **没有任何网元 SDK 依赖**（不含 Netconf/SNMP/TR-069 等库）；
3. **没有任何凭据配置项**（无 Token、无账号、无密钥；唯一地址是 `http://127.0.0.1:11434` 本地 Ollama）；
4. **休眠决策的输出对象是 CSV 与日志文件**，不是设备。

> 审核方可直接检索仓库验证：全仓库不含 `requests.post`、`snmp`、`netconf`、`ssh` 等调用。

### 5.4 数据合规

- 仅使用**扇区级聚合统计量**，从数据源头规避个人信息；
- MVP 阶段全部使用**合成数据**，不接触任何运营商现网数据；
- 试验网阶段数据仅在内网流转，保留期不超过试验周期 + 30 天。

### 5.5 安全设计上的保守性

即使在"纯记录"模式下，本项目仍内置了三重保守机制：

1. **QoS 硬约束**：未服务比例超阈值即放弃休眠；
2. **独立复核**：QoS 校验不复用打分结果，而是重新计算一次；
3. **突发回滚**：负载跳变超 25 个百分点立即撤销休眠、回到全开。

即：**宁可少省电，也不冒用户体验风险。**

## 6. 初步仿真验证结果

MVP 阶段已在**本地 CPU**完成 24 小时（96 个决策周期）全量回放，使用 6 扇区合成流量数据，得到三组策略对照（详表见 §6.1）：

| 策略 | 节能率 | 加权未服务比例 | 峰值未服务比例 | 一句话结论 |
|---|---|---|---|---|
| A 全开基线 | — | 0.0000% | 0.000% | 最费电，但不掉线 |
| B 随机休眠 | 20.64% | 0.1146% | 1.500% | 省了电，但**越过了 QoS 红线** |
| **C Agent 智能休眠** | **29.22%** | **0.1462%** | **1.000%** | 省电最多，且**全程不越线** |

### 6.1 实测数据表

**试验设置**：单小区 6 扇区、24 小时、96 个决策周期（15 min/周期）、合成流量（固定种子可复现）、本地 CPU 运行。

| 策略 | 总能耗 (kWh) | 节能率 | 未服务用户比例（加权） | 峰值未服务比例 | 休眠扇区·周期数 |
|---|---|---|---|---|---|
| A 全开基线 | 119.254 | — | 0.0000% | 0.000% | 0 |
| B 随机休眠基线 | 94.637 | 20.64% | 0.1146% | **1.500%** | 131 |
| **C Agent 智能休眠** | **84.407** | **29.22%** | **0.1462%** | **1.000%** | 186 |

**关键发现（三条，均有数据支撑）**：

1. **Agent 的节能幅度显著高于随机策略**：29.22% vs 20.64%，多节省 10.19 kWh/日。原因是 Agent 会主动挑选"静态功耗占比高、迁移代价小"的扇区，而随机策略只是碰运气。

2. **随机策略实际上已经越过了 QoS 红线**：其峰值未服务比例达到 **1.500%**，超出 1% 的约束上限；而 Agent 的峰值恰好压在 **1.000%**，96 个决策周期**全部合规**。这正是"有 QoS 硬约束"与"没有"的本质差别。

3. **Agent 用满了 QoS 预算来换节能**：Agent 的加权未服务率（0.1462%）略高于随机策略（0.1146%），因为打分函数中 `w_e(1.0) > w_q(0.8)`，算法会主动把体验余量兑换成节电量——但**始终不越线**。这一取舍是显式可调的：把 `w_q` 调高，Agent 就会更保守。

**运行稳定性**：

| 指标 | 数值 |
|---|---|
| 决策周期总数 | 96 |
| 突发流量回滚次数 | 0（该日无超过 25 个百分点的负载跳变） |
| 单周期决策耗时（不含 LLM） | 约 20 ms |
| 24 小时全量回放耗时 | 约 2 秒（`--no-llm`） |
| LLM 解释条数（组合变化时触发） | 20 条 / 96 周期 |

### 6.2 扩展验证：7 天连续回放

为验证"跨天是否会出现决策漂移"，用同一套模型再跑 672 个决策周期（7 天）：

| 指标 | 单日（96 周期） | 7 天连续（672 周期） | 差异 |
|---|---|---|---|
| 全开基线能耗 | 119.25 kWh | 834.66 kWh | — |
| Agent 能耗 | 84.41 kWh | 589.78 kWh | — |
| **节能率** | **29.22%** | **29.34%** | +0.12 pp |
| **加权未服务率** | **0.1462%** | **0.1491%** | +0.0029 pp |
| 休眠扇区·周期数 | 186 | 1306 | — |
| 突发回滚次数 | 0 | 0 | 0 |

**结论**：7 天节能率与单日仅相差 0.12 个百分点，未服务率稳定在 0.15% 量级，说明决策过程**不存在跨天累积漂移**，可长期稳定运行。这也为《验证计划》中的 7 天试验设计提供了方法学预演。

### 6.3 结果解读要点

1. **Agent 的节能幅度显著高于"什么都不做"**，同时未服务比例严格控制在 1% 以内（峰值 1.000%，96 周期无一越线）；
2. **随机休眠的对照价值**：它比 Agent 少省 8.58 个百分点，却在个别周期把未服务比例推到 1.5% —— 证明了"能不能自动睡"不是重点，"睡了之后有没有人把关"才是。单纯追求节能率是危险的；
3. **休眠时段分布呈"扇区差异化"而非"统一凌晨"**：校园区/办公区扇区在 00:00–08:00 整段休眠，商业区扇区在上午低负载时段休眠，工业区在傍晚后休眠。这说明 Agent 是在按每个扇区的真实话务特征做决策，而不是套用一条全局时间规则（详见 `sim/result/fig_sleep_heatmap.png`）；
4. **决策平滑性**：加入切换代价项后，功率曲线不再在阈值边界反复横跳，代价是节能率从 31.18% 微降到 29.22%。在真实网络中，这一交换可以避免扇区频繁开关带来的信令开销与硬件损耗。

> 说明：以上为**合成数据**的仿真结果，仅用于验证决策链路的正确性，**不代表真实网络中的节能幅度**。真实量级需在试验网阶段以只读 KPI 验证（见《验证计划》）。

## 7. 算力说明

| 项 | 说明 |
|---|---|
| 计算位置 | **全部在本地 CPU 完成** |
| GPU | **不需要** |
| 云端大模型集群 | **不需要** |
| 模型训练 | **无训练过程**（权重为显式配置，非学习所得） |
| LLM 推理 | Ollama 本地运行 ≤ 1B 参数小模型（约 400 MB），CPU 即可 |
| 24h 全量回放耗时 | **约 2 秒**（不含 LLM 解释）；含 LLM 解释约 1.5 分钟 |
| 内存占用 | < 1 GB |

**结论**：本项目对算力的要求极低，普通办公笔记本即可完整运行，不存在算力资源申请诉求。
