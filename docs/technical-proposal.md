# 技术方案（Technical Proposal）

**项目名称**：基于 LangGraph 的小区扇区自主休眠节能调度 Agent
**申报方向**：紫金山实验室 Pre6G 试验网开发者计划 —— 网络智能运维 / 绿色节能
**文档版本**：v1.0
**编制日期**：2026-10-21

---

## 0. 一句话概述

用**确定性决策图（LangGraph）**替代"人拍脑袋 + 定时脚本"的粗放节能方式：每个 15 分钟决策周期，Agent 读取小区各扇区负载与在线用户数，枚举可行的休眠组合，在**节能收益**与**用户 QoS 损失**之间做加权择优，QoS 越界即放弃休眠；大模型只负责把决策结果翻译成人话，**不参与任何数值判定**。

---

## 1. 总体架构

### 1.1 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│  L5 展示与审计层   对比报表 / 时序曲线 / 决策审计日志          │
├──────────────────────────────────────────────────────────────┤
│  L4 解释层         Ollama 本地小模型（仅生成自然语言说明）      │
├──────────────────────────────────────────────────────────────┤
│  L3 决策图层       LangGraph：7 节点确定性有向图 + 1 条条件边   │
│                    (读状态 → 筛候选 → 打分 → 择优 → QoS校验    │
│                     → 审计回滚 → 解释)                         │
├──────────────────────────────────────────────────────────────┤
│  L2 工具层         3 个纯函数工具（无随机、无 LLM）             │
│                    get_sector_state / estimate_energy_saving   │
│                    / estimate_qos_impact                       │
├──────────────────────────────────────────────────────────────┤
│  L1 数据源层       仿真合成流量 CSV（MVP）                      │
│                    → 试验网阶段替换为「只读 KPI 接口」          │
└──────────────────────────────────────────────────────────────┘
```

### 1.2 数据流

```
合成/只读流量  ──►  扇区状态快照  ──►  候选集合  ──►  组合打分表
                                                          │
                                                   最优休眠方案
                                                          │
                                            ┌─────────────┴─────────────┐
                                        QoS 校验通过                QoS 校验越界
                                            │                           │
                                     执行休眠（仅记录）          放弃休眠（保持全开）
                                            └─────────────┬─────────────┘
                                                     审计与回滚
                                                          │
                                                  LLM 生成解释文本
                                                          │
                                              写入结果 CSV / 审计日志
```

> **重要**：图中的"执行休眠"在本项目中**只是在内存与日志里记录一个决策结果**，不产生任何面向真实基站的配置指令。详见 §6 接口使用规划。

## 2. 核心调度算法

### 2.1 能耗模型

单扇区采用线性"静态 + 动态"功耗模型（公开文献中的常见形式）：

```
P_on(load) = (P_static + P_dyn_max × load/100) × hw_factor
P_sleep    = P_sleep_base × hw_factor
ΔE(combo, T) = Σ_{i∈combo} [P_on(load_i) − P_sleep] × T / 1000   [kWh]
```

| 参数 | 取值 | 含义 |
|---|---|---|
| `P_static` | 760 W | 与话务无关的固定开销（功放偏置、基带常开部分等） |
| `P_dyn_max` | 440 W | 满载相对静态部分的增量功耗 |
| `P_sleep_base` | 25 W | 深度休眠残留功耗 |
| `hw_factor` | 0.975 ~ 1.025 | 由扇区编号确定性生成的硬件差异系数 |
| `T` | 0.25 h | 单个决策周期时长 |

**关键洞察**：低负载扇区的功耗主要来自 `P_static`，因此**休眠低负载扇区的边际节能效率最高**——这正是本方案把优化目标锁定在"夜间低负载扇区"的原因。

### 2.2 QoS 影响模型

休眠扇区的用户需要由同小区邻区"吸收"，因此存在两级损失：

```
hole      = U_sleep × HOLE_RATE                      # 覆盖空洞（切换失败/盲区）
residual  = Σ_{j∉combo} C × max(0, 0.85 − load_j/100)  # 邻区可吸收余量
overflow  = max(0, U_sleep − residual)                # 容量溢出
U_unserved = min(U_sleep, hole + overflow)
ratio      = U_unserved / U_total_cell
```

| 参数 | 取值 | 含义 |
|---|---|---|
| `HOLE_RATE` | 0.02 | 即使邻区有余量，仍有 2% 用户因覆盖/切换原因掉线 |
| `C` | 100 用户 | 单扇区用户容量 |
| `0.85` | 安全边际 | 只把 85% 容量视为可对外吸收 |

该模型是**两级扣减**的：先扣覆盖空洞，再扣容量溢出，二者取和且不超过迁移用户总数，避免出现"未服务用户 > 休眠扇区用户"的荒谬结果。

### 2.3 加权多目标择优

对每个候选组合 `c ∈ C`（`C` 为候选扇区的幂集）：

```
score(c) = w_e × ΔE(c) − w_q × U_unserved(c) − w_s × S(c)

其中 S(c) = |c △ P_prev|   # 与上一轮实际配置的对称差，即需要切换的扇区数

约束：
  (1) ratio(c) ≤ qos_constraint            # 默认 1%
  (2) E_plan(c) ≤ energy_budget            # 全开能耗 × (1 − 10%)
```

| 权重 | 取值 | 设计意图 |
|---|---|---|
| `w_e` | 1.0 | 每节省 1 kWh 的收益 |
| `w_q` | 0.8 | 每造成 1 个用户未服务的惩罚（1 个用户 ≈ 0.8 kWh 代价） |
| `w_s` | 0.08 | 每切换 1 个扇区状态（休眠↔唤醒）的代价 |

**切换代价项（`w_s`）解决的是"决策抖动"问题**：当某扇区负载恰好卡在阈值附近时，若只看节能与 QoS，算法会每个周期都在"休眠/唤醒"之间来回横跳。在真实网络里，扇区频繁开关会带来额外的信令开销、硬件损耗与用户侧的接入时延。加入 `S(c)` 后，算法会倾向于维持上一轮配置，只在节能收益明显大于切换代价时才改变决策。

实测效果：加入该项后，24 小时功率曲线的剧烈波动基本消失，节能率从 31.18% 微降至 29.22%，而未服务率从 0.1659% 降到 0.1462% —— 也就是**用 2 个百分点的节能换取了更平滑、更工程可用的运行曲线**，这个交换是划算的。

`w_q` 的含义是**把用户体验折算成可比的能量成本**：只有当"多睡一个扇区"带来的节能量大于其造成的用户损失折算值时，才会被选中。这是一条显式的、可审计的价值判断，而不是模型的主观偏好。

**复杂度**：候选扇区数 `n ≤ 12` 时全量枚举（`2^n ≤ 4096`），MVP 场景 `n = 6`，仅 64 种组合，单周期计算耗时 < 5 ms；`n > 12` 时自动切换为贪心增量策略，保证在更大规模小区下仍可实时收敛。

### 2.4 为什么不用强化学习 / 不做在线训练

| 方案 | 可解释性 | 可复现性 | 冷启动风险 | 结论 |
|---|---|---|---|---|
| 规则阈值（定时休眠） | 高 | 高 | 低 | 精度差，无法权衡 QoS |
| 强化学习（DQN/PPO） | 低 | 低（随机性、训练不稳定） | 高 | 不满足"可审计"要求 |
| **加权多目标枚举（本方案）** | **高** | **高（同一输入必得同一输出）** | **无** | **采纳** |

试验网阶段的首要目标是**积累可信的对照数据**，而非追求极限节能率。确定性算法能保证每一条决策都可被逐项复算，这是向审核方证明"节能没有以牺牲用户为代价"的前提。

## 3. LangGraph 决策图设计

### 3.1 全局状态（State）

```python
class AgentState(TypedDict, total=False):
    current_time: str                                  # 当前决策时刻
    sector_states: Dict[str, Dict[str, Any]]           # 扇区快照：负载/用户/活跃/休眠权限
    energy_budget: float                               # 本时段能耗上限（kWh）
    qos_constraint: float                              # 最大未服务用户占比（默认 0.01）
    decision_history: List[Dict[str, Any]]             # 最近 10 轮决策（审计/回滚依据）
    scratch: Dict[str, Any]                            # 单轮临时黑板（不进审计）
```

`scratch` 是流程内部的中转区，承载候选集合、打分表、拟执行方案等中间量；它的生命周期仅限一次 `invoke`，因此**不会污染业务状态，也不会进入审计日志**。

### 3.2 节点与边

| 序号 | 节点 | 输入 | 输出 | 计算性质 |
|---|---|---|---|---|
| ① | `read_state` | `current_time` | `sector_states` / `energy_budget` | 只读 IO + 基准能耗计算 |
| ② | `filter_candidates` | `sector_states` | 候选扇区列表 | 规则过滤（`sleepable ∧ active`） |
| ③ | `score_combinations` | 候选 + 状态 | 全量打分表 + 最优解 | 组合枚举 + 加权打分 |
| ④ | `select_best` | 打分表 | `selected_plan` | 取 `max(score)`，不做新计算 |
| ⑤ | `qos_check` | `selected_plan` | `qos_passed` | **独立复核**（重算，不复用③的结果） |
| ⑥a | `apply_decision` | ⑤通过 | 本周期能耗记录 | 状态应用（仅记录） |
| ⑥b | `abort_all_on` | ⑤拒绝 | 全开能耗记录 | 保守降级 |
| ⑦ | `audit_and_rollback` | ⑥输出 | `decision_history` | 突发检测 + 历史截断 |
| ⑧ | `explain` | 审计记录 | 自然语言说明 | **唯一调用 LLM 的节点** |

条件边：`qos_check --(passed)--> apply_decision`；`qos_check --(rejected)--> abort_all_on`。

### 3.3 ⑤ 号节点的"独立复核"设计

容易忽略但很重要的一点：QoS 校验**不是**复用节点③的打分结果，而是重新调用一次 `estimate_qos_impact` 做独立复算。

理由是防御性编程——若节点③在枚举或过滤时存在逻辑缺陷（例如把不可行解误判为可行），独立复核仍能拦住越界方案。代价是每周期多一次微不足道的计算（< 1 ms），换来的是"**任何情况下都不会因为上游 bug 而牺牲用户**"的保证。

### 3.4 决策历史的数据结构

每轮审计记录包含：

```json
{
  "time": "2026-01-15 03:15:00",
  "action": "sleep",
  "sleeping_sectors": ["CELL-A-SEC-01", "CELL-A-SEC-05"],
  "step_energy_kwh": 2.914,
  "baseline_energy_kwh": 3.517,
  "total_load_pct": 4.1,
  "total_users": 14,
  "qos_verify": {"unserved_ratio": 0.0061, "limit": 0.01, "passed": true},
  "energy_budget_kwh": 3.165,
  "score": 0.597,
  "rollback": false,
  "rollback_reason": "",
  "explanation": "…",
  "explanation_source": "ollama"
}
```

`explanation_source` 区分 `ollama` 与 `template`，便于审核时确认"哪些解释来自模型、哪些来自规则模板"，避免把模型输出误当成决策依据。

## 4. 回滚与审计机制

### 4.1 突发流量自动回滚

```
if (load_now − load_prev) > 25 个百分点 and 本轮存在休眠扇区:
        撤销本轮休眠 → 回滚至上一轮稳定配置（全开）
        在审计记录中标记 rollback=True 并写入触发原因
```

阈值 25 个百分点来自对合成数据的观察（正常时段间负载波动 < 8 个百分点），可在 `tools/constants.py` 中按实际网络调整。

### 4.2 回滚的保守原则

回滚时一律回到**全开**，而不是"回到上一轮的休眠组合"。原因：突发流量往往伴随用户位置变化，上一轮的休眠组合在新话务分布下未必安全；全开是唯一无需再评估的安全状态。

### 4.3 历史窗口

`decision_history` 固定保留最近 10 轮（2.5 小时）。窗口内足以覆盖一次典型的话务突发与恢复过程，同时保证内存占用恒定，可长期无人值守运行。

## 5. LLM 的定位（本方案的核心边界）

| 维度 | LLM 做了什么 | LLM 没做什么 |
|---|---|---|
| 输入 | 已定稿的结构化决策结果 | 原始话务数据、候选组合 |
| 输出 | 2~3 句中文解释文本 | 任何数值、任何扇区选择 |
| 失败影响 | 解释退化为规则模板，决策不变 | 不影响能耗/QoS 任何指标 |
| 可复现性 | `temperature=0` | 决策不依赖 LLM 输出 |

**工程保证**：`explain` 节点的返回值只写 `scratch["last_record"]["explanation"]`，**不触碰** `sector_states` / `energy_budget` / `decision_history` 的数值字段。即使把模型换成一个"胡言乱语"的模型，调度结果也不会有任何变化。

**兜底路径**：Ollama 未启动、模型未下载、推理超时（60 s）——三种情况都会自动降级为代码模板解释：

> "2026-01-15 03:15:00 小区处于低负载时段，休眠 2 个低负载扇区（CELL-A-SEC-01, CELL-A-SEC-05），本周期节省约 0.603 kWh，预计未服务用户比例 0.61%，低于 1% 的约束上限。"

这段话完全由代码拼装，无模型参与，信息量与 LLM 输出等价。

## 6. 接口使用规划（严格只读 + 模拟回传）

### 6.1 申请的接口（白名单）

| 接口 | 方向 | 数据内容 | 频率 | 权限性质 |
|---|---|---|---|---|
| 小区扇区负载查询 | 读 | 扇区级 PRB 利用率、在线用户数 | 15 min | **只读** |
| 扇区状态查询 | 读 | 扇区开关状态、可休眠能力标识 | 15 min | **只读** |
| 模拟决策日志上传 | 写（单向） | Agent 决策记录 JSON（仅归档） | 15 min | **仅日志落地，不触达网元** |

### 6.2 明确不申请的权限

- ❌ 基站配置下发（`SET`/`MODIFY` 类网元操作）
- ❌ 扇区载波关断 / 小区闭塞（Cell Locking / Cell Shutdown）
- ❌ 任何 SNMP Set、NETCONF edit-config、RESTCONF PUT/PATCH 写接口
- ❌ 任何直接登录网元设备的通道（SSH / Telnet / 带外管理）

### 6.3 数据流向

```
试验网只读 KPI ──(单向)──► Agent 本地进程 ──► 决策日志 ──(单向)──► 日志服务器
                                   │
                                   └──► 结果报表（离线）
```

全程**单向**：数据只进不出（除日志归档），不存在"Agent → 网元"的指令通道。这一约束在代码层面体现为：整个仓库没有任何 HTTP 写方法、没有任何网元 SDK 依赖、没有任何凭据配置项。

### 6.4 合规自查

- ✅ 仓库内无硬编码密钥/账号/Token（仅有 `OLLAMA_HOST=127.0.0.1` 这一本地地址）
- ✅ 数据源为合成数据，不含任何用户标识信息（无 IMSI/SUPI/手机号/位置）
- ✅ 决策结果为"建议/记录"性质，不构成对现网的任何操作

## 8. 可复现性设计

1. **固定随机种子**：合成流量 `seed=42`、随机基线 `seed=7`，任何人重跑得到逐字节一致的数据；
2. **无隐式状态**：工具函数均为纯函数（输入相同 → 输出相同），唯一的全局状态是数据源单例的只读缓存；
3. **LLM 不参与数值**：`temperature=0` + 位置隔离，双重保证；
4. **决策可复算**：审计记录同时保存 `baseline_energy_kwh`、`step_energy_kwh`、`qos_verify`，审核方可直接按 §2 的公式手工验算；
5. **版本锁定**：`requirements.txt` 固定主要依赖版本区间，避免环境漂移。

## 9. 已知局限与后续演进

| 局限 | 影响 | 演进方向 |
|---|---|---|
| QoS 模型为解析式近似，未考虑真实无线信道 | 未服务比例是估算值，非实测值 | 试验网阶段用只读 KPI 中的真实掉线率反向校准 `HOLE_RATE` |
| 仅单小区 6 扇区，未建模跨小区协同 | 邻区吸收能力被高估或低估 | 扩展为多小区多 Agent 协同（见 README 迭代计划） |
| 未考虑业务类型（VoLTE/URLLC/普通数据） | 关键业务用户与普通用户等价处理 | 引入业务权重，URLLC 用户禁止迁移 |
| 未接入语义通信流量特征 | 6G 场景适配不足 | 结合 Pre6G 语义通信试验数据，将"语义重要性"纳入 QoS 权重 |
| 载波/功率级节能手段未建模 | 节能空间被低估 | 增加符号关断、通道关断等多级节能状态 |
